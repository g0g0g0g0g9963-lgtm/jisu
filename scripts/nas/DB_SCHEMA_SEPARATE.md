# 운영 DB 구조 변경 — 별도 적용 절차

이 문서는 **배포 센터의 일반 코드 업데이트에 포함되지 않는 작업**을 전산 담당자가 별도 변경 건으로 검토할 때 사용합니다. 이번 GitHub 브랜치의 운영 서버는 시작할 때 테이블·컬럼·인덱스를 생성하거나 변경하지 않습니다. 필요한 구조가 없으면 DB를 건드리지 않고 시작을 중단합니다. 요구되는 테이블·컬럼은 `server/db-schema-check.mjs`에 명시되어 있습니다. `qa/db-test-schema.mjs`는 시험 DB 전용이며 NAS 실행 이미지에 복사되지 않습니다.

1. **변경 계획 승인:** 운영 DB의 실제 `sqlite_master`와 `PRAGMA table_info`를 확인하고, 부족한 구조에 대한 SQL을 별도 변경 건으로 작성·검토합니다. 기존 예약의 `owner_id`/`owner_email` 연결은 이름 일치만으로 결정하지 말고 검증된 회사 계정과 예약 내역을 대조해 별도 승인합니다. 이 브랜치의 배포가 소유권을 자동 할당하지 않습니다.
2. **복구 연습:** 운영 DB의 복사본으로 마이그레이션과 복구를 먼저 시험합니다. `PRAGMA integrity_check`가 `ok`인지, 예약 건수·대표 예약 ID·소유권·겹침 검사 결과가 전후에 맞는지 확인합니다. 복구 가능한 이전 앱 버전과 예상 중단 시간을 정합니다.
3. **운영 백업:** 예약 입력을 중단하고 NAS에서 `docker compose stop meeting-rooms`로 앱을 정지합니다. `/volume1/sh-pf/docker/meeting-room/data/`의 `bookings.sqlite`와 존재하는 `bookings.sqlite-wal`·`bookings.sqlite-shm`을 **같은 시점의 한 묶음**으로 웹 공개 경로 밖에 복사합니다. 파일 권한과 체크섬을 기록하고 별도 저장소에도 보관합니다. `.env`의 비밀값은 Git이나 배포 ZIP에 넣지 않습니다.
4. **별도 DB 적용:** 승인된 SQL만 운영 DB에 적용합니다. 적용 후 `PRAGMA integrity_check`, 스키마 목록, 예약 건수, 검증된 기존 예약의 소유권을 다시 확인합니다. 이 단계는 배포 센터 자동 업데이트나 `npm start`에서 실행하지 않습니다.
5. **앱 배포와 확인:** DB 검증이 끝난 뒤 이 브랜치의 앱을 배포합니다. 정상 기동, 기존 예약 조회, 신규 예약 충돌 방지, 공용 모니터 조회·예약을 확인한 후 예약 입력을 재개합니다.
6. **실패 시 복구:** 앱을 정지하고 실패한 `bookings.sqlite*` 파일을 별도 격리 폴더로 **이동해 보존**합니다. 3단계의 파일 묶음을 `data/`에 복사해 권한을 확인하고 이전 앱 버전으로 재시작합니다. 무결성·예약 건수·대표 예약을 확인합니다. 백업 이후 새로 생긴 예약은 복구로 사라질 수 있으므로, 중단 기간에는 예약 입력을 계속 막아야 합니다.

백업 파일은 세션과 개인정보를 포함할 수 있으므로 접근 권한과 보관 기간을 전산 담당자가 정합니다. 이 문서는 운영 DB를 변경하도록 승인하는 문서가 아닙니다.
