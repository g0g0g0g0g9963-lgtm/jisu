# NAS 자동 업데이트

코드가 수정되면 NAS가 **스스로** 최신 코드를 받아 다시 빌드합니다.
아래 설정을 **한 번만** 해두면, 이후에는 손댈 일이 없습니다.

동작 방식은 이렇습니다.

```
코드 수정 → GitHub에 올림 → NAS가 5분마다 확인 → 새 코드가 있으면
자동으로 받아서 다시 빌드 → 브라우저 새로고침하면 반영
```

예약 데이터(`data/`)와 SSO 설정(`.env`)은 업데이트해도 **그대로 유지**됩니다.

---

## 1단계 — GitHub 읽기 전용 토큰 만들기

저장소가 비공개라서 NAS가 코드를 받으려면 토큰이 필요합니다.
**읽기 전용**이라 이 토큰으로는 코드를 바꿀 수 없습니다.

1. https://github.com/settings/personal-access-tokens/new 접속
2. 아래대로 설정합니다.

   | 항목 | 값 |
   | --- | --- |
   | Token name | `nas-meeting-room` |
   | Expiration | 원하는 기간 (예: 1년) |
   | Repository access | **Only select repositories** → `jisu` 선택 |
   | Permissions → Repository permissions → **Contents** | **Read-only** |

3. `Generate token`을 누르고 나온 값(`github_pat_...`)을 복사합니다.
   이 화면을 벗어나면 다시 볼 수 없으니 바로 다음 단계로 넘어가세요.

> 만료되면 자동 업데이트가 멈추고 `auto-update.log`에 실패가 기록됩니다.
> 그때는 토큰을 새로 만들어 2단계만 다시 실행하면 됩니다.

## 2단계 — NAS에서 설정 스크립트 실행

SSH로 NAS에 접속해서 아래를 실행합니다.

```sh
cd /volume1/sh-pf/docker/meeting-room
sh scripts/nas/setup-auto-update.sh
```

`scripts` 폴더가 아직 없다면, 이 저장소의 `scripts/nas/` 두 파일을 먼저
같은 경로에 올려두고 실행하세요.

스크립트가 하는 일:

1. `data/`와 `.env`를 백업합니다 (`../meeting-room-backup-<날짜>`)
2. 토큰을 물어봅니다 (화면에 표시되지 않습니다)
3. 폴더를 GitHub와 연결하고 최신 코드로 맞춥니다
4. 등록할 명령을 알려줍니다

## 3단계 — DSM 작업 스케줄러에 등록

**제어판 → 작업 스케줄러 → 생성 → 예약된 작업 → 사용자 정의 스크립트**

| 항목 | 값 |
| --- | --- |
| 작업 이름 | `회의실 예약 자동 업데이트` |
| 사용자 | `root` |
| 일정 | 매일 / **5분 간격으로 반복** |
| 사용자 정의 스크립트 | `sh /volume1/sh-pf/docker/meeting-room/scripts/nas/auto-update.sh` |

저장한 뒤 목록에서 해당 작업을 선택하고 **실행**을 눌러 한 번 확인해 보세요.

## 확인하는 방법

```sh
tail -f /volume1/sh-pf/docker/meeting-room/auto-update.log
```

- 새 코드가 없으면 **아무것도 기록하지 않습니다** (로그가 조용한 게 정상)
- 업데이트가 있으면 이렇게 남습니다.

```
2026-08-13 06:46:54  새 코드 발견: fd04229 -> ddee989
2026-08-13 06:46:54  적용할 변경: ddee989 회의실 정보 카드 여백 축소
2026-08-13 06:46:54  컨테이너를 다시 빌드합니다…
2026-08-13 06:48:10  [완료] ddee989 적용됨. 사이트 정상 응답.
```

## 안전장치

- **예약 데이터는 지워지지 않습니다.** `data/`와 `.env`는 Git이 추적하지 않아
  업데이트 대상에서 제외됩니다.
- **빌드가 실패하면 기존 사이트가 계속 돌아갑니다.** 새 컨테이너가 뜨지 못하면
  이전 컨테이너가 그대로 유지되고, 로그에 실패가 기록됩니다.
- **빌드 후 응답까지 확인합니다.** 사이트가 뜨지 않으면 로그에 경고를 남깁니다.
- **겹쳐 실행되지 않습니다.** 빌드가 5분을 넘겨도 다음 차례는 건너뜁니다.
- 토큰은 `.git/deploy-credentials`에 소유자만 읽을 수 있는 권한(600)으로 저장되고,
  저장소에는 올라가지 않습니다.

## 자동 업데이트를 멈추려면

작업 스케줄러에서 해당 작업의 체크를 해제하면 됩니다.

## 되돌리려면

주의: 프로그램 버전 복귀와 예약 DB 복원은 별개입니다. 기존 `data/`를 과거 백업으로
덮어쓰면 이후 예약이 사라질 수 있습니다. DB 구조 호환성과 최근 예약 보존을 확인하고,
자동 업데이트 작업을 중단한 상태에서 전산 담당자의 승인 후 진행하세요.

설정할 때 만들어진 백업 폴더(`../meeting-room-backup-<날짜>`)에 이전 `data/`와
`.env`가 들어 있습니다. 특정 시점 코드로 돌아가려면:

```sh
cd /volume1/sh-pf/docker/meeting-room
git log --oneline          # 원하는 시점의 앞 7자리 확인
git reset --hard <그 값>
docker compose up -d --build
```

## 관리자 전용 운영 페이지

- 진입: 회사 Microsoft 계정으로 로그인한 뒤 예약 화면 오른쪽 위 **관리자 모드**. 직접 주소는 `/admin`입니다.
  일반 직원은 메뉴가 보이지 않으며 주소/API 직접 접근도 서버에서 차단합니다.
- NAS의 비공개 `.env`에 `ADMIN_MS_EMAIL`을 허용할 회사 MS 로그인 이메일 **한 개**로 설정합니다.
  값이 없으면 모두 차단됩니다. 이메일은 소스나 프런트엔드 설정에 넣지 않습니다.
- 가능하면 `ADMIN_MS_OBJECT_ID`에 해당 직원의 Entra 개체 ID도 지정하세요.
  없으면 최초로 인증된 해당 이메일의 개체 ID를 DB에 고정합니다. 이름 변경은 허용하지만
  같은 이메일을 다른 계정에 재사용한 경우는 차단합니다. 계정 교체 시 전산 담당자가
  검증한 새 개체 ID를 환경설정에 명시해야 합니다. 관리자 페이지에서 권한 변경은 제공하지 않습니다.
- 기존 Microsoft SSO 설정이 필요합니다. 익명 개발 모드는 관리자 권한을 받을 수 없습니다.
  코드 업로드만으로 NAS의 `.env` 값이 변경되지는 않습니다.
- 새 환경설정은 승인된 배포/컨테이너 재생성 후 반영됩니다. 이 기능 개발 자체로 NAS를 배포하지 않습니다.

### 실제 제공되는 기능과 설정 필요 항목

- **이용 통계**: 예약일 기준 기간 선택(최근 30일 기본, 이번 달/최근 90일/최대 366일 직접 선택),
  예약 건수·예약자 수·예약 시간, 예약자 상위 10명, 회의실별 예약 현황, 24개 시간대별 예약 건수.
  `/api/admin/usage` 역시 서버 관리자 권한으로 보호되고 캐시에 저장하지 않습니다.
  직원은 고유 계정 ID로 구분하며 ID가 없는 과거 데이터는 이메일로 구분합니다. 두 값이 모두 없으면
  전체 예약 건수에는 포함하되 직원 순위에서는 제외합니다. 같은 이름을 한 사람으로 합치지 않습니다.
  집계는 현재 남아 있는 예약 및 보존된 종료 이력 기준이며, 삭제된 미래 예약은 제외합니다.
  반복 예약은 날짜별 1건, 수정은 추가 건수로 세지 않습니다. 1시간 구간과 겹친 예약은 각 구간에 포함되므로
  시간대별 건수 합계는 전체 예약 건수보다 클 수 있습니다. 사이트 방문·로그인 횟수나 실제 출석 통계는 아닙니다.
- 예약 생성·변경·취소와 감사 이력을 같은 트랜잭션에 기록합니다. 적용 이전 이력은 복원하지 않습니다.
  이력에는 직원 개체 ID·이름·시각·예약 ID·회의실/날짜/시간 전후 값과 변경한 항목명만 저장합니다.
  목적/참석자 상세값, 이메일, 로그인 토큰은 별도 감사 이력에 복사하지 않습니다.
- 예약 조회 지연, 저장 서버 오류, DB 잠금 오류는 최근 5분 최대 5,000개 표본으로 표시합니다.
  표본은 재시작 시 초기화됩니다. 이는 외부 가용성 감시나 이메일/Teams 알림이 아닙니다.
- `BACKUP_DIR`를 비공개 영구 저장 위치로 지정하면 수동 백업/검사가 활성화됩니다.
  현재 볼륨 구성에서 `/app/data/backups`는 같은 NAS의 로컬 백업일 뿐입니다.
  다른 경로는 전산 담당자가 영구 볼륨·접근 권한·암호화를 별도 구성해야 합니다.
  `public`/`dist` 등 웹 공개 위치는 사용하지 마세요. 백업에는 기존 DB의 로그인 세션도 포함됩니다.
- `BACKUP_INTERVAL_MINUTES=60`은 매시간 자동 백업 예시이며 기본값 `0`은 자동 실행 안 함입니다.
  `BACKUP_MAX_FILES=168`에 도달하면 오래된 파일을 임의 삭제하지 않고 새 백업을 실패 처리합니다.
  전산팀이 별도 장비 복사·보관 기간·정리 작업을 확정하고 백업 성공 시각을 외부에서 감시해야 합니다.
- 백업은 SQLite Online Backup API로 생성하며 worker에서 무결성/스키마/건수를 검사합니다.
  이는 별도 환경에서 앱을 띄워 생성·수정·취소를 실행하는 **실제 복원 시험을 대체하지 않습니다**.
- 운영 DB 복원·배포 되돌리기 실행 버튼은 없습니다. 안내와 미연결 상태만 표시합니다.
  DB 복원 시 신규 예약과 감사 이력을 보존하고, 복원된 기존 세션을 명시적으로 무효화해 재로그인하세요.
  `SESSION_SECRET` 재발급만으로 DB에 보관된 세션이 무효화되지는 않습니다.
- `OPS_PRIMARY_CONTACT`/`OPS_SECONDARY_CONTACT`는 담당자 표시용이며 실제 알림을 발송하지 않습니다.
  경보 기준은 `OPS_SLOW_REQUEST_MS`(기본 2000), `OPS_DISK_WARNING_PERCENT`(기본 20)로 설정합니다.
- 운영 전 감사 이력 보관 기간, 읽기 권한, 접근 통제된 외부 보관, 복원 목표와 연락 체계를 확정하세요.

### 격리 검증

`node qa-admin.mjs`는 실제 Microsoft/NAS와 통신하지 않고 `data-qa-admin/` 아래 시험 DB로
계정/주소/API 접근 제한, 개체 ID 고정, 감사 이력의 원자성, 백업 및 검사를 검증합니다.
`QA_PLAYWRIGHT_MODULE`과 `QA_BROWSER`를 설정하면 PC/모바일 화면도 검사합니다.

## 공용 모니터 전용 화면

- 직원용 `/` 화면과 별개의 `/kiosk` 주소 및 전용 화면입니다. 직원 사이트에 메뉴를 추가하지 않습니다.
  두 화면은 같은 서버의 예약 DB와 겹침 검사 트랜잭션을 사용합니다. 별도 예약 DB를 만들지 마세요.
- 기본값은 비활성입니다. 승인된 NAS 설정에서 `KIOSK_ENABLED=1`과 충분히 무작위인
  `KIOSK_PAIRING_CODE`(32자 이상)를 지정한 뒤, 공용 브라우저의 연결 화면에 코드로 연결합니다.
  운영에서는 `APP_BASE_URL`의 HTTPS 원본과 일치해야 합니다. 비밀 코드는 Git·URL·화면 캡처·로그에 넣지 않습니다.
- 이 코드는 기기 연결 권한입니다. 직원에게 배포하지 말고 전산담당자가 승인된 모니터에서만 입력하세요.
  연결 코드를 변경하고 서버를 재시작하면 기존 공용 세션도 무효화됩니다. 개인 MS 로그인이나
  관리자 로그인은 공용 기기 연결을 대신하지 않습니다. 네트워크/브라우저 정책도 관리하세요.
  기기 연결은 30일 후 만료되므로 전산담당자가 재연결할 수 있는 관리 절차를 마련하세요.
- 공용 화면은 9층/12층 선택, 회의실별 주간 보기, 좌우 스크롤, 한 번 터치 예약을 제공합니다.
  예약자 이름은 매번 빈 값이며 필수입니다. 이름·입력 내용은 브라우저 저장소에 기억하지 않습니다.
- 공용 입력 이름은 **본인 인증 정보가 아닙니다**. `source=kiosk`로 기록하고 직원의 MS ID/이메일은
  부여하지 않습니다. 개인 계정의 ‘내 예약’으로 이름만 연결하거나 수정·삭제 권한을 주지 않습니다.
  공용 API는 목록 조회와 단건 생성만 허용하며, 본부·목적·참석자·이메일은 공용 목록에 내보내지 않습니다.
- 공용 예약도 전체 건수·회의실·시간대 통계에는 포함되지만, 확인된 직원별 순위에는 합치지 않습니다.
  공용 입력자의 확인·예약 관리/취소 절차는 운영 전 별도로 확정해야 합니다.
- 공용 예약의 개인 Outlook 자동 추가와 회사 회의실 Outlook 예약 가져오기는 포함하지 않습니다.
  기존 Outlook과 공동 사용하려면 앞서 정리한 회의실 메일함·권한·승인/충돌 연동이 추가로 필요합니다.
- 요청 응답이 끊겨도 같은 예약 요청 키로 결과를 재확인하여 중복 저장을 막습니다.
  별도 검증 환경에서 기기 연결/해제, 권한 차단, 중복 예약, 재시도, 터치 스크롤 및 입력 초기화를 시험하세요.

## 직원 검색 · 즐겨찾기 · Outlook 개인 일정

### 회사 계정 연동 전 필수 설정

- Microsoft Entra의 기존 앱 등록에 **위임 권한** `User.ReadBasic.All`, `Calendars.ReadWrite`를 추가하고
  회사 정책에 따른 관리자 동의를 받습니다. 무인 애플리케이션 권한이나 회사 전체 일정 쓰기 권한은 사용하지 않습니다.
- 기존 로그인은 `openid profile email`을 유지합니다. 직원이 예약창의 **Microsoft 계정 연결**을 누를 때만
  위 권한 및 `offline_access`를 추가 요청합니다. 기존과 동일한 `/auth/callback`을 사용합니다.
  다른 계정을 선택하면 연결을 거부합니다. 회사 Exchange Online 사서함/라이선스가 있어야 합니다.
- NAS의 비공개 환경설정에 `MICROSOFT_TOKEN_KEY`(무작위 32바이트를 Base64로 인코딩)를 한 번 생성해 저장합니다.
  생성 예: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.
  이 키는 Git, 이미지, 화면 캡처, 로그에 남기지 말고 DB 백업과 **별도** 비밀 저장소에 보관하세요.
  AES-256-GCM으로 계정에 결합해 토큰을 암호화합니다. 키를 잃거나 바꾸면 각 직원의 재연결이 필요합니다.
- `OUTLOOK_REMINDER_MINUTES` 기본값은 10분입니다. 서버의 업무 시간대 설정을 사용하며 24:00은 다음 날 00:00으로 변환합니다.
- 코드만 저장해도 회사 권한/비밀키/배포 설정은 변경되지 않습니다. 실제 테넌트 동의·실기기 알림 검증 후 배포하세요.

### 기능 범위 및 실패 처리

- 예약자는 인증된 본인으로 고정됩니다. 직원 참석자는 이름 대신 MS 개체 ID로 저장하고, 같은 이름도 이메일로 구분합니다.
  연결 전에는 이 사이트에 로그인한 직원만 검색됩니다. 연결 후에는 회사 디렉터리에서 이름/이메일의 앞부분으로 검색합니다.
  검색은 최대 20명씩 표시합니다. 본부 자동 입력은 별도 전산 확인 후 진행하며 이번 기능은 본부 정보를 요청하지 않습니다.
- 선택된 직원의 이메일/ID는 예약자에게만 보여줍니다. 직원 선택은 참석자 기록이며 **초대 메일 발송이 아닙니다**.
  직접 이름 입력은 미확인 외부 참석자용입니다. 회사 전체 직원 내보내기 기능은 제공하지 않습니다.
- 즐겨찾기는 계정의 고유 ID에 저장하므로 기기/세션이 바뀌어도 유지됩니다. 익명 미리보기는 해당 브라우저에만 저장합니다.
  기존 시간표의 회의실 순서는 변경하지 않고 선택창의 전체/즐겨찾기 필터로 모아 봅니다.
- 기능 적용 이후 회사 계정으로 만든 예약은 예약 저장과 동시에 동기화 작업을 DB에 기록합니다.
  예약 저장 성공과 Outlook 반영 성공은 별개이며 예약창에서 최근 반영 상태를 확인할 수 있습니다.
  연결이 안 되어 있으면 연결 후 처리합니다. 적용 이전 예약을 일괄 등록하거나 기존 Outlook 일정을 가져오지는 않습니다.
- **본인 개인 일정만** 생성합니다. 참석자/회의실 리소스 초대, Teams 온라인 회의, Teams 채팅/봇 알림은 만들지 않습니다.
  예약 사이트를 기준으로 생성·수정·취소를 단방향 반영합니다. Outlook에서 직접 수정한 내용은 예약 사이트로 들어오지 않습니다.
  Outlook에서 직접 삭제해 이후 수정이 실패한 경우 자동으로 새 일정을 만들지 않고 확인 필요 상태로 남깁니다.
- 외부 요청은 12초 제한, 저장된 작업은 재시작 후 이어집니다. 응답 유실 시 같은 `transactionId`와 최초 본문으로 재시도합니다.
  일시적 장애는 지수형 지연/Retry-After를 적용하고 8회 이후 확인 필요로 표시합니다. 권한 만료는 재연결이 필요합니다.
  예약은 자동 재전송하지 않습니다. 진행 중 생성과 취소가 겹쳐도 생성된 이벤트 ID를 보존해 취소 작업을 이어갑니다.
- 동일 DB를 여러 서버에서 운용하는 구성은 지원 범위 밖입니다. SQLite 단일 앱 인스턴스로 운영하고,
  DB 복원/서버 시각 급변/장시간 중단 후에는 예약과 Outlook 반영 내역을 대조하세요. 백업에는 암호화된 토큰,
  참석자 기본 정보와 작업 큐도 포함되므로 세션과 동일하게 보호하고 보관 기간을 정해야 합니다.
- `offline_access` 연결은 로그아웃 후에도 예약 변경/취소 반영에 사용됩니다. 화면의 연결 관리 → Microsoft 연결 해제로
  저장된 토큰을 삭제할 수 있습니다. 기존 Outlook 일정은 유지되고 진행 중인 요청은 완료될 수 있습니다.
  이후 변경/취소는 재연결 전까지 반영되지 않습니다. 회사의 앱 권한 철회 시에도 재연결 전까지 중단됩니다.
- 같은 Microsoft 365 계정에서는 Outlook/Teams 일정이 공유되지만, Outlook 알림과 Teams 시작/일정 알림은
  동일하지 않습니다. Teams 클라이언트·OS·개인 알림 설정을 별도 점검하고 두 제품 모두 실기기로 확인하세요.

### 격리 검증

`node qa-convenience.mjs`는 가상 Microsoft 응답과 `data-qa-convenience/` 시험 DB만 사용합니다.
동명이인 ID 유지, 계정별 즐겨찾기, 다른 계정 연결 차단, 토큰 암호화/갱신, 일정 생성·수정·취소,
응답 유실과 재시작 중복 방지, 생성 중 취소, 권한 거부와 자정 경계를 확인합니다.
브라우저 검사는 위와 동일한 `QA_PLAYWRIGHT_MODULE`, `QA_BROWSER` 설정으로 추가합니다.
